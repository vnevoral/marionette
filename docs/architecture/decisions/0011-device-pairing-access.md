# ADR-0011: Access from paired devices (device token)

- **Status**: Accepted
- **Date**: 2026-09-26

## Context

NFR-01 has so far excluded authentication from the MVP, citing a trusted
network. On 2026-09-26 the project owner clarified the deployment and the
requirement:

- the service runs in the internal network, from outside it is reachable
  via VPN;
- access is to be limited to the owner's "safe" devices;
- verification is to happen **once** when the client is connected, after
  that the client is no longer verified — no repeated password entry.

The threat we address: another device in the internal network or in the
VPN (a guest, a compromised IoT device, a coworker) opens the UI or calls
the API and runs an action on the host. We do not address compromise of
the host itself or of a paired device.

Environment constraints: access via VPN typically over plain HTTP to an IP
address or internal name, i.e. without TLS and without a "secure context"
in the browser.

## Decision

Access to the API (except health and pairing) requires a **device token**
in a cookie. A device obtains the token with a one-time **pairing code**:

1. The first code is generated by the service at startup if it has no
   paired device, and it is written to the log (`journalctl -u
   marionette`). Whoever reads the service log on the host is an authorized
   operator.
2. Further codes are generated by the UI on an already paired device
   (Devices → Pair a new device).
3. Code: 8 characters of Crockford Base32, valid for 10 minutes, one-time,
   invalidated after 5 failures, in memory only.
4. Token: 256 bits from `crypto/rand`, cookie `marionette_device`
   (`HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` under TLS or per
   `MARIONETTE_COOKIE_SECURE`). On disk only a SHA-256 hash in
   `devices.json` (0600) next to the configuration. A device not used for
   the validity period expires; the validity is
   `MARIONETTE_DEVICE_EXPIRY_DAYS` (default 60, range 1–400, the upper
   bound is the browsers' cookie limit) and the cookie's `Max-Age` has the
   same duration. Usage renews both the cookie and the last-used time at
   most once a day.
5. List of devices and their removal in the UI; recovery of lost access by
   deleting `devices.json` and restarting.
6. `MARIONETTE_AUTH=off` turns verification off for development; the
   service logs it as a warning at startup. The default is on.

NFR-12 (cross-site protection) stays unchanged; `SameSite=Strict`
complements it, does not replace it.

Approved by the owner 2026-09-26: first code in the service log, validity
shortened from 180 to 60 days and configurable, no tokens for scripts.

## Considered alternatives

- **Password / HTTP Basic auth** — rejected: the owner explicitly does not
  want repeated entry; the browser does remember the password, but Basic
  auth has no logout or device management and the password is sent with
  every request.
- **Passkeys (WebAuthn)** — the strongest binding to the device, but it
  requires a secure context (HTTPS or `localhost`), which access via VPN
  over HTTP does not have, and a confirmation (biometrics/PIN) at every
  sign-in. Rejected for this phase; can be added later as a second pairing
  method once there is TLS.
- **Client TLS certificates (mTLS)** — a real binding to the device, but
  it requires TLS in the application, a custom CA and manual installation
  of the certificate on every device; disproportionate for a single
  operator.
- **IP address allowlist** — VPN addresses may change and it does not
  distinguish two devices behind the same address; rejected as the main
  mechanism.
- **Relying on the VPN only (the state so far)** — does not address the
  threat from the internal network, which the owner wants to cover.
- **Bearer token in a header for scripts** — out of scope; no non-browser
  client exists today. Can be added later ("API tokens") on top of the
  same device storage.

## Consequences

- Each device is paired once; after that access requires nothing more,
  until the device deletes its cookies, uses a different browser or the
  operator removes it.
- The cookie is bound to the browser, not to the hardware: whoever copies
  the cookie from a paired device gains access. This is mitigated by
  `HttpOnly` (JS cannot read it), the VPN and the ability to remove a
  device. A stronger binding = passkeys/mTLS (see alternatives).
- Without TLS the token travels over the network unencrypted; in a
  deployment behind a VPN the tunnel is encrypted. With direct LAN access
  without a VPN the token can be sniffed — the README will recommend a TLS
  proxy and `MARIONETTE_COOKIE_SECURE=always`.
- New API: pairing endpoints and device management; all other API
  responses can be `401`. The SPA needs a pairing screen and a Devices
  page; the E2E suite pairs as part of its setup.
- `curl` without a token stops working (except health); the documentation
  and the installation procedure will be updated.
- A new state file `devices.json`; backups and restore must be mentioned
  in the documentation.
